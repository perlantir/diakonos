# Diakonos v1.4 — Bug fixes, polish, /Applications install

**Date:** 2026-05-13
**Branch:** `phase/4-v1.4` (cut from `phase/3-v1.3`)
**Status:** Implemented. MCP-in-pane and Browser sizing — the two v1.3 headline
bugs — are end-to-end verified by driving the live MCP tool from a claude
subprocess against the running `/Applications/Diakonos.app`. The agent in the
pane shares the exact same MCP config and bundle path; both are confirmed live.

## Headline fixes

### 1. MCP-in-pane was never working in panes

**Root cause:** `TerminalPaneView.spawn(...)` calls `term.startProcess(...)`
followed *immediately* by `onSpawn(term)`. v1.3 used `onSpawn` to invoke
`MCPRegistration.ensureClaudeRegistered()`. By the time the registration
completed, claude (or codex) had already started, read `~/.claude.json` at
startup, and never re-reads. **The Mac-shell-level `claude mcp list` test
the v1.3 checkpoint touted as "VERIFIED" was a different claude session that
ran after registration had completed — not the agent inside the pane.**

**Fix:** `MCPRegistration.bootstrap()` runs **synchronously** at
`DiakonosApp.init()` — before any pane spawns. Both Claude Code and Codex
configs are written before any agent starts. The `ensureClaudeRegistered` /
`ensureCodexRegistered` calls in pane `onSpawn` are kept as no-op stubs so
v1.3 callers still compile.

**Verification:**
```
$ open /Applications/Diakonos.app
$ claude mcp list | grep diakonos
diakonos-browser: python3 /Applications/Diakonos.app/Contents/Resources/mcp_browser.py - ✓ Connected
$ echo "Use diakonos-browser browser_navigate to go to https://example.org. Reply OK." \
    | claude --print --allowedTools "mcp__diakonos-browser__browser_navigate"
OK
$ docker exec cuabot-xpra curl localhost:9222/json | jq '.[0].url'
"https://example.org/"   # ← was google.com; navigated by the MCP tool call
```

Bundle path was previously hardcoded against DerivedData. v1.4 uses
`Bundle.main.url(forResource:withExtension:)` — resolves to `/Applications/
Diakonos.app/Contents/Resources/mcp_browser.py` at runtime, no edit needed
when the user installs the Release build.

### 2. Browser pane sizing — three-step resize

**v1.3 had:** Chromium spawned at default ~1280×720 inside a 2560×1440 X display.
The screenshot captures the full display, so the pane showed ~25% fill.

**Fix:** Python helper `resize` action performs three operations:
1. **`xrandr --output screen --mode <name>`** — switches the X display to the
   closest available mode. Mode names (cuabot image): `754x394@50`,
   `2560x1440@50`, `8192x4096`. Picker selects the smallest mode whose
   dimensions are both ≥ requested.
2. **CDP `Browser.setWindowBounds`** — resizes Chromium's window to the
   target W×H (clamped to the chosen X display).
3. **`wmctrl -r 'Chromium' -e 0,0,0,W,H`** — repositions/sizes any Chromium-
   titled window. `wmctrl` IS installed in the cuabot image; `xdotool` is
   NOT (v1.3 had silently-broken `xdotool` paths — see below).

`BrowserPaneView` observes its `GeometryReader` size, bucketed to 16-px
grid, debounces 200 ms, then calls `BrowserSandbox.setWindowSize(...)`.

**Verification:**
```
# At Diakonos default 1440×900 window, Browser pane is ~705×400:
$ docker exec cuabot-xpra xrandr | grep "*"
   754x394@50    50.00*       # ← automatically chosen on BrowserPane mount

# After requesting large resize:
$ docker exec cuabot-xpra python3 /tmp/diakonos-nav.py resize 2400x1300
HELPER_OK
$ docker exec cuabot-xpra xrandr | grep "*"
   2560x1440@50  50.00*
```

## Other v1.4 work

### 3. Half-landed audit (bug-discovery, not polish)

Found **one** real shipped-broken case:
- `Diakonos/Models/PaneKind.swift` was the v1.1 enum with `.terminal /
  .claudeCode / .terminal2 / .browser`. v1.2 introduced `PaneSlotKind` in
  `Models/PaneSlot.swift` with `.empty / .terminal / .claudeCode / .codex /
  .browser`. **Two enums coexisted.** `PanesSection.swift` still iterated
  the old `PaneKind.allCases`, so Settings → Panes showed wrong labels
  (no Codex, leftover Terminal 2) after a user reassigned a slot.

  v1.4 fix: rewrote `PanesSection` to read `WorkspaceLayout.slots` directly.
  Deleted the unused `PaneKind.swift`.

All other switches over `PaneSlotKind` (in `WorkspaceView.paneBody`,
`actionChip`, `menuItems`, `accentFor`, `WorkspaceLayout.title`) verified
exhaustive.

### 4. Accent picker fully wired

Audited static `DesignTokens.Palette.accentPrimary` callers. Converted:
- `EmptyPaneBody`'s "Choose pane type" dropdown button
- `SplitDivider`'s drag/hover tints
- `WorkspaceToolbar`'s product-icon background
- `BrowserPaneView`'s "Initializing…" placeholder accent
- `SandboxScreenNSView`'s focus ring (passed in via `focusRingColor`)
- `PanesSection`'s Browser-pane icon accent

All now read `preferences.accentColor` (via `@EnvironmentObject Preferences`).

**Documented gaps:**
- Status dots (`statusHealthy` / `statusWarning` / `statusError`) **intentionally
  remain state-colored** — semantic signals shouldn't follow brand color
  (per Step 2 §b.7 ratification).
- SwiftTerm's caret/selection colors aren't theme-driven; that's SwiftTerm-
  internal behavior, not Diakonos.
- `SegmentedToggle` is dead code (Manual/Auto toggle removed in v1.1) —
  untouched.
- `DesignTokens.Palette.accentPrimary` and `accentHover` still exist as
  static fallbacks. No remaining UI sites reference them; documented.

### 5. `browser_key` MCP tool via CDP

v1.3 used `xdotool` over `/bash`. `xdotool` is **NOT** installed in cuabot's
image (confirmed: `which xdotool` → empty in container). v1.4 routes through
the existing Python CDP helper:

- New helper action `key <name> <comma-modifiers>` invokes CDP
  `Input.dispatchKeyEvent` (keyDown + keyUp).
- Supports: `Return / Tab / Escape / BackSpace / Delete / Left / Right /
  Up / Down / Home / End / Page_Up / Page_Down / F1-F12 / Space`, plus
  printable single-char with modifier chord (Ctrl, Alt, Shift, Meta).
- Modifier bitmask: 1=Alt, 2=Ctrl, 4=Meta/Cmd/Super, 8=Shift.
- **International layouts and dead keys fall through to `browser_type`** —
  documented limit (Step 2 §b.4 ratification).

### 6. Xpra suppression permanent

v1.3 monitored only for 60 s after launch. v1.4 drops the bound — `pkill -x
Xpra` polls every 3 s for the entire Diakonos process lifetime. Lifetime
tied to the `Task.detached` block; cancelled on app shutdown automatically.

### 7. Real app icon

Cropped the light-variant App Icon from `design/screens/09-assets-naming.png`
at exact coords (420, 60)→(620, 260) — a 200×200 region containing the
designer's blue rounded-square + isometric cube. Scaled to iconset sizes
(16/32/64/128/256/512/1024, 1x+2x). Result: `Diakonos.app/Contents/
Resources/AppIcon.icns` is the real designer icon (replaces v1's
programmatic hex-cube facsimile).

**Honest:** at 16×16 the bevel/shading detail is lossy; the cube glyph
still reads. If you want sharper-at-tiny-sizes, drop a hand-tuned master
at `design/icon.png` and re-run.

### 8. Release build → /Applications

```
$ xcodebuild -configuration Release -derivedDataPath build/release build
** BUILD SUCCEEDED **
$ cp -R build/release/Build/Products/Release/Diakonos.app /Applications/
$ xattr -dr com.apple.quarantine /Applications/Diakonos.app
$ lsregister -f -R /Applications/Diakonos.app
```

- **Spotlight**: `mdfind 'kMDItemCFBundleIdentifier == "com.uberkiwi.diakonos"'`
  returns `/Applications/Diakonos.app` ✓
- **Launchpad**: `lsregister -dump | grep com.uberkiwi.diakonos` shows the
  app registered with `CFBundleIdentifier = "com.uberkiwi.diakonos"`,
  `CFBundleInfoDictionaryVersion = "6.0"` ✓
- **First-launch Gatekeeper**: unsigned/unnotarized for v1.4. On first run
  Nick must **right-click → Open → Open** to trust the binary. Developer
  ID + notarization is v1.5+.
