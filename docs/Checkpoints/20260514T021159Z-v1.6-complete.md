## Headlines

### 1. Unified keyboard pipeline (THE headline)

v1.5 had two keyboard pipelines — CDP for chat panes, xdotool-via-cuabot
for the Browser pane — plus several broken keys. v1.6 collapses to one
classifier (`KeyboardEventTranslator`) and one backend (`CDPInput`).

**What's fixed:**

- **Shifted symbols** (`!@#$%^&*()_+`, `{}|:"<>?`, `~`, …) — v1.5
  treated *any* modifier (including Shift) as a "control modifier" and
  routed the chord, so Chromium got `keydown.key="@"` and dropped it.
  v1.6 routes Shift/Option as *typing modifiers*; the composed
  printable char goes through `dispatchType`.
- **Option-key diacritics** (`é`, `ç`, `´` dead key) — same bug class
  as shifted symbols. Fixed by the same policy.
- **F1-F12** — v1.5 had no mapping; v1.6 maps them in both the
  translator and `CDPInput.dispatchKey`.
- **Numpad** — NSEvent.characters resolves numpad digits to the
  printed char, so they flow through `.type` automatically. Numpad
  Enter (keyCode 76) is routed as Return.
- **Repeat keys** — keyDown autorepeat already worked structurally;
  no change needed.

**What's structurally improved:**

- Browser pane keyboard moved from xdotool (which was unreliable —
  xdotool isn't always present in cuabot's image) to CDP on port 9222.
- `SandboxInput.type` / `.key` are now dead code; left in place for
  bisect safety. Removal is a v1.7 chore.

**Empirical verification:** ran `scripts/keyboard_cdp_harness.py`
through the cuabot `/bash` proxy against the live container Chromium.
27/27 PASS. Output reproduced in `Docs/v1.6-spec.md` §1. The harness
sends every printable char category + every named special + every
clipboard chord (Cmd+A/C/V/X/Z, Cmd+Shift+Z) directly via CDP and
verifies the resulting textarea / keydown event.

**What that proves and doesn't:**
- Proves: CDP `Input.dispatchKeyEvent` accepts the shapes Swift sends
  and Chromium fires the right `keydown`/`input` events. No fabricated
  API surface here.
- Doesn't prove: that macOS delivers the right `NSEvent` for every
  key (Diakonos's keyDown path is upstream of CDP). Nick verifies by
  typing.

### 2. Clipboard bridge

`Diakonos/Services/ClipboardBridge.swift` glues Mac NSPasteboard and the
sandbox Chromium's clipboard:

- **Cmd+V**: read `NSPasteboard.general.string` → dispatchType into the
  sandbox. The chord is NOT forwarded (would clobber with empty paste).
- **Cmd+C**: evaluate `window.getSelection().toString()` in the sandbox,
  write to NSPasteboard. Chord IS forwarded so page-native handlers fire.
- **Cmd+X**: same as Cmd+C; Chromium's native handler does the cut.
- **Cmd+A**: just a chord (no clipboard side-effect).

Limitations documented in spec: text-only (no images / rich types),
~3s latency for 10K-char pastes (acceptable).

### 3. 6-pane mode (NEW)

Toolbar gains a 4/6 segmented control. 4-pane (2×2, default) and 6-pane
(2×3, three columns) coexist; toggling preserves state. Cmd+1..6 focus
shortcuts map to reading order:

- 4-pane: 1=TL, 2=TR, 3=BL, 4=BR (matches v1.5 muscle memory).
- 6-pane: 1=TL, 2=TM, 3=TR, 4=BL, 5=BM, 6=BR.

Persistence: `WorkspaceLayout` always stores 6 slots in
`workspaceLayout.v2` (UserDefaults JSON). `paneCount` controls visibility.
6→4 with non-empty `.topMid`/`.bottomMid` triggers an NSAlert confirm
("these middle-column panes will be hidden but their state will be
preserved when you switch back to 6-pane").

v1.5 `workspaceLayout.slots.v1` data is auto-migrated on first launch
(four slots promoted into the six-slot array; middles seeded `.empty`;
paneCount=4).

### 4. Half-landed audit — structurally killed

`PaneSlotKind.userSelectable` is now the single source of truth for the
EmptyPaneBody dropdown. It's derived from `allCases` minus `.empty`, so
adding a new pane kind to the enum automatically surfaces it in the UI.
In DEBUG, an assertion fires if a case is missing from the display-order
array. In release, the missing case is appended at the end — degraded
UX, not silently missing. The class of bug that bit v1.3 (missed
Codex) and v1.5 (missed claudeChat/chatgptChat) is no longer possible.

## Honest gaps

### Routing verification — still blocked

Step 3 §4 ("verify v1.5's blocked routing test") requires a logged-in
claude.ai / chatgpt.com session. v1.5 documented the same blocker. I
cannot log in on Nick's behalf. The ChatBridge plumbing was not
modified in v1.6, but I've eyeballed the call sites and they still
look correct: poll → trigger detect → routeAndPostback → DOM scrape →
agent invocation → postback. Once Nick logs in, the test sequence is
unchanged from v1.5's spec.

### NSEvent → translator classification is unit-test-equivalent only

The translator's classification of NSEvent into routes is *reasoned*
correct: Shift/Option are typing modifiers, Cmd/Ctrl are command
modifiers, named specials always route through key, etc. But Diakonos
v1 doesn't run XCTest, so there's no automated check. The empirical
test harness validates the CDP layer; the NSEvent layer requires Nick
typing at a real pane.

### Clipboard is text-only

Image / rich-mime-type clipboard transfers are not implemented. Pasting
an image silently does nothing. Documented; v1.7 candidate.

### Browser pane keyboard regression risk

v1.6 switched the Browser pane's keyboard from xdotool to CDP. The
xdotool path may have been working for some keys; the CDP path is now
the only path. If Nick sees a regression, the symptoms will be obvious
(typing or a chord does nothing). Mitigation: `SandboxInput.type` /
`.key` are still present and could be wired back as a fallback if
needed.
