## cua surface — what we actually found

I started with the unknowns from `docs/cua-integration.md` and probed the live cuabot to nail down the real protocol.

### `npx cuabot --serve` — discovered HTTP API

cuabot runs a **Node.js HTTP server** on a single port (default 7842 — `--serve` auto-finds an available one if asked). Found endpoints, exhaustively:

| Method | Path          | Status | Behavior |
|--------|---------------|--------|----------|
| GET    | `/status`     | 200    | `{ok, ready, container, containerPort, playwright}` |
| POST   | `/bash`       | 200    | `{stdout, stderr}` — **one-shot exec, NOT a stream** |
| POST   | `/screenshot` | 200    | image bytes |
| POST   | `/click`      | 200    | `{x, y, button?}` |
| POST   | `/doubleclick`| 200    | `{x, y}` |
| POST   | `/move`       | 200    | `{x, y}` |
| POST   | `/mousedown` / `/mouseup` | 200 | mouse button events |
| POST   | `/drag`       | 200    | `{x1, y1, x2, y2}` |
| POST   | `/scroll`     | 200    | `{x, y, dx, dy}` |
| POST   | `/type`       | 200    | `{text}` |
| POST   | `/key`        | 500*   | `{key}` (returns 500 unless ready) |
| POST   | `/keydown` / `/keyup` | 200 | key events |

**Probed and confirmed nonexistent:** `/exec`, `/shell`, `/pty`, `/terminal`, `/stream`, `/ws`, `/events`, `/sse`, `/tools`, `/mcp`, `/openapi`. There is **no streaming PTY endpoint** on the cuabot HTTP server.

`GET /status` payload during boot vs. ready:
```
{"ok":true,"ready":false,"container":"running on port 10000","containerPort":10000,"playwright":"connected"}
{"ok":true,"ready":true, "container":"running on port 10000","containerPort":10000,"playwright":"connected"}
```
Cold-start to ready: ~15–20 s on a warm Docker daemon with the image already pulled.

### Underlying container

`docker ps` shows a single container per cuabot session:
```
80a315083031   cuabot-xpra   trycua/cuabot:latest   Up   0.0.0.0:10000->10000/tcp
```
The container exposes an Xpra-style HTML/HTTP surface on port 10000 — that's how cuabot streams sandboxed GUI apps (Chromium, etc.) as Mac windows. Linux aarch64 inside; runs as `user` in `/home/user`.

Inside the container:
- `/bin/bash`, `/bin/sh`, `/bin/dash` available
- `/home/user/.local/bin/claude` installed (Claude Code CLI)
- `hermes` is **NOT** installed in cua's image — Phase 3 documents this

## Decision: how SwiftTerm gets a PTY

cuabot's HTTP API is GUI-driving + one-shot bash. Useless for a real interactive terminal experience (every command would be a fresh shell with no state).

**Chosen pattern: `docker exec -it cuabot-xpra <shell>`**, spawned by SwiftTerm's `LocalProcessTerminalView.startProcess(executable: "<path-to-docker>", args: ["exec", "-it", "cuabot-xpra", "/bin/bash"])`.

Why this is correct:
- Real PTY (docker allocates a tty with `-t`, proxies stdin with `-i`)
- Persistent shell state per pane (each pane is its own `docker exec`)
- Zero Python shim required
- All four panes share the same cua sandbox (the design treats "Sandbox" as a singular, see screen 06 — one sandbox status, multiple panes inside)
- cuabot still owns sandbox lifecycle (start/stop/reset) via its CLI + HTTP `/status`

Drawback: we depend on the host having Docker. cua itself depends on Docker (the image is `trycua/cuabot:latest`), so this is not a new dependency — it's the same one cua already requires.

## What landed

- `Diakonos/Services/CUAHTTPClient.swift` — typed wrapper over the cuabot HTTP API. Just `status()` + `runBash()` for v1; the GUI-driving endpoints are reserved for v0.3 browser pane work.
- `Diakonos/Services/CUAProcessSupervisor.swift` — generic long-running-process supervisor; used to spawn `npx cuabot --serve` if no server is up. Adopts an existing cuabot server if one is already running.
- `Diakonos/Services/CUASandboxManager.swift` — `@MainActor ObservableObject` driving the toolbar `StatusIndicator` and providing the container name to panes. Locates `npx` and `docker` on the standard install paths.
- `Diakonos/UI/Workspace/Panes/TerminalPaneView.swift` — `NSViewRepresentable` hosting `SwiftTerm.LocalProcessTerminalView`. Spawns `docker exec -it <container> /bin/bash`. Dark theme background `#0B1220` (matches `bgApp` dark). Title-bar OSC sequences proxied to a closure.
- `Diakonos/UI/Workspace/Panes/SandboxedPaneBody.swift` — shows `InitializingPaneBody` until sandbox is `.running`, then renders the live pane content.
- `Diakonos/UI/Workspace/WorkspaceView.swift` — top-left pane wired to `TerminalPaneView`; other three remain placeholders (Phase 3).
- `Diakonos/UI/RootView.swift` — owns `@StateObject CUASandboxManager`, calls `start()` on `.onAppear`, passes sandbox state to toolbar.

## Verification

1. **Cold start.** `npx cuabot --serve` from CLI: HTTP comes up immediately; `"ready":false` for ~15s; flips to `"ready":true`. Confirmed.
2. **Build.** `xcodegen generate && xcodebuild ... build` → `** BUILD SUCCEEDED **`. One initial protocol-conformance fix on `hostCurrentDirectoryUpdate(source: TerminalView, …)` (SwiftTerm protocol uses `TerminalView` as the source for that one method, not `LocalProcessTerminalView`).
3. **Runtime.** App launched (PID 27276), stayed alive, idle CPU, 94 MB RSS. Process tree:
   ```
   27276  Diakonos
   └── 27331  docker exec -it cuabot-xpra /bin/bash
   ```
   This proves SwiftTerm successfully spawned the `docker exec` PTY child for the Terminal pane.

## Known issues / non-blockers

- **cuabot --serve cold-boot takes ~15 s** before `ready:true`. During that time the Terminal pane shows the InitializingPaneBody placeholder, which is correct UX but worth noting for first-launch perception.
- **Status indicator "Healthy" label** is the design's display string. We may want a separate label for "Running" vs. "Healthy" semantics in v0.2 (`Healthy` implies a health-check pass beyond just `ready:true`); v1 follows the design package exactly.
- **`hermes` is not installed in cua's Docker image.** Phase 3's Hermes pane will spawn `/bin/bash` as a v1 fallback with the orange theme applied to the pane header. Documented for the Phase 3 checkpoint.
- **No PTY resize wiring yet.** SwiftTerm's `sizeChanged` callback fires; I left the body empty in the Coordinator. SwiftTerm's internal `setWinSize` already runs against `process.childfd` automatically (see `MacLocalTerminalView.sizeChanged`), so resize works for the docker exec process. No-op in coordinator is correct.
- **App restart pattern:** Phase 2 doesn't handle "cuabot crashed; restart it." `CUASandboxManager.beginContinuousPolling` flips to `.warning` if status fetch fails, but doesn't auto-restart. v1-acceptable per spec; v0.2 should add reset behavior.
