## Root cause

`ChatBridge` had two interacting issues:

1. **`TriggerDetector.classify` returns `.continueThread`** for any
   plain user-authored message when `activeThreadTarget != nil`
   (`TriggerDetector.swift:75-77`).
2. **`ChatBridge.handle`'s `.continueThread` arm calls `runRoute`
   unconditionally**, regardless of postback mode
   (`ChatBridge.swift:267-270`, pre-patch).

When the user manually pressed Send on Diakonos's textarea-posted
reply, claude.ai produced a new user-authored DOM node containing that
exact text. The 3-second poll scraped it, `TriggerDetector` saw an
active thread, returned `.continueThread`, and `handle` dispatched
the reply back to `claude --print` as a new task — the echo loop.

JSONL trace from session `23bf2391-...` (2026-05-15 17:20-21Z):
- 17:20:28 — `route_detected` (Nick types `Code: pwd`)
- 17:20:49 — `route_posted` (reply lands in textarea)
- 17:21:09 — `route_detected` **again** (20 s later — Nick pressed
  Send; the posted reply became a user message and re-routed)

Session `fc8c9753-...` shows the same loop cascading **4 times** in
~90 seconds before Nick pressed Stop.

## Fix — exact code changes in `Diakonos/Services/ChatBridge.swift`

Three deltas, layered:

### 1. Per-conversation posted-content hash ledger (state)

```swift
private let postedHashesLRUCap = 20
private var pendingPostedHashes: [String: [Int]] = [:]
private var lastPostedRouteID:   [String: UUID] = [:]
```

Whitespace-normalized `String.hashValue` of each posted reply body.
LRU-bounded at 20 per conversation. `lastPostedRouteID` lets us emit
a clean `route_closed` event tied to the right `routeID` when echo
is detected.

### 2. Hash-dedupe skip in `poll`

After scraping the latest user message, before calling `handle`:

```swift
if isEchoOfRecentPostback(message: msg, conversationID: convo) {
    noteRouteClosed(conversationID: convo,
        detail: "Diakonos's posted reply was sent — route closed (echo dedupe)")
} else {
    await handle(...)
}
```

`noteRouteClosed` appends a `route_closed` JSONL event for
`lastPostedRouteID[convo]` and clears the route pointer. The state
machine itself is local to `runRoute` and out of scope here; the
JSONL log is the source of truth.

### 3. Manual mode: no implicit continuation

`handle`'s `.continueThread` arm:

```swift
case .continueThread(let payload):
    guard postbackMode.sendsAutomatically else {
        DiagnosticsLog.shared.log(.info,
            "Manual mode: plain user message in active thread — no route (use Code:/Codex: to start a new route)")
        return
    }
    guard let thread = threads[conversationID] else { return }
    await runRoute(...)
```

`PostbackMode.sendsAutomatically` is true for `.autoSend` and
`.fullAuto` only. Manual mode never auto-continues — every route
requires an explicit `Code:` / `Codex:` prefix.

### 4. Record hash after every postback

In `runRoute` after `postReply`:

```swift
recordPostedHash(result.body, conversationID: conversationID, routeID: envelope.routeID)
```

### 5. Exit: clears echo state

`.exit` arm also clears `pendingPostedHashes[convo]` and
`lastPostedRouteID[convo]` so a fresh thread starts cleanly.

## Why v1.7's 11/11 trigger-safety tests missed this

The v1.7 standalone harness (`trigger_safety_test.swift` and
`postback_mode_test.swift`) tested **string classification in
isolation**. Inputs were strings; outputs were classifier verdicts.
The tests covered escape, quote, code-block, message-start, and
even `"plain message with active thread → continuation"` — they
verified the continuation behavior **as the intended outcome**.

The harness had no notion of "this user message was generated by
Diakonos's own postback in turn N-1." There was no round-trip
fixture: route fires → reply captured → posted → re-scraped on
next poll.

The fix's test mirror (`/tmp/echo_loop_test.swift`, also persisted
to `scripts/echo_loop_test.swift`) plugs that gap. It runs the full
state cycle and verifies that re-scraping a posted body returns
`ECHO`, not `CONT_ROUTE`.

in-memory only. If Nick refreshes the chat tab AND the textarea still

the bug being fixed — the bug was the recurring loop within one
session — but the brief asks for this check and I want the limit
explicit. A persistent on-disk hash store is a v1.7.2 polish.
