# v1.1 — Sandboxed Chromium browser pane (Approach A)

**Branch:** `phase/1-v1.1`
**Timestamp:** 2026-05-13T14:07:58Z

## Result: Approach A works

cuabot's container `cuabot-xpra` already runs an Xpra WebSocket server on port
10000 (verified: `Server: Xpra-WebSocket-Server Python/3.10`) with a live X
session on `:100`. Chromium is pre-installed at `/usr/bin/chromium`. So the
pipeline is:

1. **Diakonos's BrowserPaneView** mounts a `WKWebView` pointed at
   `http://localhost:10000/` — cuabot's Xpra HTML5 client page.
2. **BrowserSandbox** (a slim, Browser-pane-local replacement for v1's
   `CUASandboxManager`) probes `GET http://localhost:7842/status`, adopts the
   server if one's up, spawns `npx cuabot --serve 7842` if not.
3. On state flip to `.running`, the URL bar's `onAppear`-triggered
   `navigate(to:)` POSTs `/bash` to cuabot:
   `DISPLAY=:100 setsid chromium --no-sandbox --no-first-run … '<URL>' > log 2>&1 &`
4. Chromium launches inside the sandbox on `:100`.
5. Xpra streams Chromium's display to the WKWebView via its WebSocket.

No fall to B (floating Mac window), C (VNC), or D (WKWebView host browser)
required.

## URL bar implementation

| Action       | Mechanism                                                                 |
|--------------|---------------------------------------------------------------------------|
| Navigate     | `POST /bash {"command": "DISPLAY=:100 setsid chromium … '<url>' &"}`      |
| Back         | `POST /bash {"command": "DISPLAY=:100 xdotool key alt+Left"}`             |
| Forward      | `POST /bash {"command": "DISPLAY=:100 xdotool key alt+Right"}`            |
| Reload       | `POST /bash {"command": "DISPLAY=:100 xdotool key F5"}`                   |

The cuabot API itself has no nav primitives; `xdotool` key injection works
because the Xpra session on `:100` exposes the X display for synthetic events.

## Honest limitations

1. **First Connect button.** When the WKWebView first loads `localhost:10000/`,
   Xpra HTML5 typically shows a "Connect" button (see `/connect.html`'s form
   structure). Auto-connect via URL params is possible
   (`?submit=true&action=connect`) but I haven't validated it end-to-end with
   the cuabot session-specific auth. **Nick will likely need to click Connect
   once on first open of the Browser pane.** v1.2 should append the autoconnect
   query string and test.

2. **Each `navigate(to:)` launches a fresh Chromium tab/window.** The current
   command unconditionally spawns Chromium. Chromium's default single-instance
   behavior usually folds new invocations into the existing window as new tabs,
   but with `--no-sandbox` this isn't guaranteed. Users typing several URLs
   in succession may accumulate tabs. v1.2 fix: use Chromium's
   `--remote-debugging-port` + CDP to navigate the existing tab.

3. **`xdotool` may not be installed in the cuabot image.** The Back/Forward/
   Reload commands silently no-op via `|| true` if it's missing. Verified
   on this machine; haven't pulled a fresh image to check.

4. **Browser pane needs Docker running.** If Docker is down or cuabot can't
   start, the pane shows the InitializingPaneBody indefinitely with an error
   message ("Sandbox initializing…" or "cuabot unreachable"). The other three
   panes work fine without Docker — they're 100% native.

5. **CSP `frame-ancestors 'self'`** on the Xpra page means embedding it in an
   iframe from another origin would be blocked. We load it directly in the
   WKWebView (not in an iframe), which is fine.

6. **Cookies / browsing history persistence:** Chromium's user-data-dir is
   inside the container's filesystem, so it survives across `docker exec`
   sessions but not across container restarts (`cuabot --reset`). That's
   intentionally sandboxed — every fresh cua boot is a clean profile.
