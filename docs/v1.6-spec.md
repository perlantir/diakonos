# Diakonos v1.6 spec

**Scope.** Three things:

1. **Keyboard pipeline unified** across all pane types. v1.5 had two
   keyboard pipelines (CDP for chat panes, xdotool-through-cuabot for the
   Browser pane) and several broken keys. v1.6 routes every pane through
   one classifier (`KeyboardEventTranslator`) and one backend (`CDPInput`).
2. **Mac ↔ sandbox clipboard bridge** (`ClipboardBridge`). Cmd+V pastes
   from the Mac clipboard into the sandbox; Cmd+C / Cmd+X copy the
   sandbox selection back to the Mac clipboard.
3. **6-pane mode** (2×3 grid). Toggled from the toolbar. The 4-pane (2×2)
   default is unchanged; 6-pane adds two middle-column slots
   (`.topMid`, `.bottomMid`) with their own Cmd+5 / Cmd+6 focus shortcuts.

Plus one structural fix: `EmptyPaneBody`'s dropdown is derived from
`PaneSlotKind.allCases`, so a new pane kind can't silently fail to appear
in the picker — the audit miss that bit v1.3 and v1.5 is now structurally
impossible.

## 1. Keyboard architecture

### Three routes

`KeyboardEventTranslator.classify(_ event: NSEvent)` returns one of:

| Route | Trigger | Backend |
|---|---|---|
| `.type(String)` | Printable text (with Shift or Option only — *typing modifiers*) | `CDPInput.dispatchType` → one `Input.dispatchKeyEvent type:'char'` per character |
| `.key(name, mods)` | Named special key (Return, Tab, arrows, F1-F12, …) OR command-modifier chord (Cmd+anything, Ctrl+anything) | `CDPInput.dispatchKey` → `keyDown` + `keyUp` with structured `key`/`code`/`windowsVirtualKeyCode`/`modifiers` |
| `.clipboardPaste` | Cmd+V | `ClipboardBridge.paste(toPort:)` — read NSPasteboard, dispatch as `type` events. **Do NOT forward the chord.** |
| `.clipboardCopy` | Cmd+C | `ClipboardBridge.copyFromBrowser(port:)` reads sandbox selection via `Runtime.evaluate`, writes to NSPasteboard. **Also forwards Cmd+C** so the page's native copy handler still fires. |
| `.clipboardCut` | Cmd+X | Same as copy but Cmd+X is forwarded; Chromium's native handler performs the cut on its side. |
| `.ignore` | Empty NSEvent.characters, control-char only | — |

### Modifier policy

- **Cmd / Ctrl** = command modifiers. Always force the `.key` (chord) route.
- **Shift / Option** = typing modifiers. They do NOT trigger the chord
  route. Shift+2 → `"@"` flows through `.type("@")`; Opt+e → dead-key `´`
  flows through `.type("´")`.
- **Named specials** (Return/Tab/arrows/F-keys/etc.) always take the `.key`
  route, regardless of modifier state.

This policy fixes the v1.5 regressions where:
- Shifted symbols (`@`, `#`, `$`, …) were sent as key chords with name
  `"@"`, which Chromium drops, because the code treated any modifier
  (including Shift) as a "control modifier."
- Option-key diacritics (`é`, `ç`) were broken for the same reason —
  Option was treated as a control modifier.

### Empirical verification

`scripts/keyboard_cdp_harness.py` drives every key category against a
live Chromium via CDP and verifies the result. Ran 27/27 PASS against
the cuabot sandbox Chromium on the 2026-05-14 build:

```
[PASS] type a-z, A-Z, 0-9, symbols (!@#$%^&*()_+{}|:"<>?~), space+punct
[PASS] key Return, Tab, Escape, BackSpace, Delete, Left/Right/Up/Down,
       Home, End, Page_Up, Page_Down, F1, F5, F12
[PASS] chord Cmd+A, Cmd+C, Cmd+V, Cmd+X, Cmd+Z, Cmd+Shift+Z
```

Run it yourself with a chat pane open:

```
python3 scripts/keyboard_cdp_harness.py --port 9223   # Claude Chat
python3 scripts/keyboard_cdp_harness.py --port 9224   # ChatGPT
```

### What's NOT verified by the harness

The harness validates the **CDP layer** (the protocol between cuabot's
Chromium and the dispatch code) but cannot validate the **NSEvent
layer** (whether macOS delivers the right NSEvent for a given key, and
whether `KeyboardEventTranslator` classifies it correctly). For that,
you have to actually run the app and try keys in a pane. The translator's
unit-test-equivalent assertions live in code comments at
`Diakonos/Services/KeyboardEventTranslator.swift`.

### Why CDP for everything

v1.5 had two keyboard pipelines:

1. **Chat panes** → `CDPInput.dispatchKey` / `dispatchType` on ports
   9223/9224 (per-pane Chromium with `--remote-debugging-port`).
2. **Browser pane** → `SandboxInput.key` / `.type` via cuabot's `/bash`
   endpoint running `xdotool key …` / `xdotool type …`.

But xdotool isn't reliably installed in cuabot's image (a comment in
`BrowserSandbox.swift` flags this), and even when it works, the two
pipelines drift over time — different mappings, different escaping,
different bugs. v1.6 collapses to one pipeline: `CDPInput` on the right
port (9222 for Browser, 9223/9224 for chat panes). `SandboxInput.click`
/ `.scroll` / `.move` (mouse-only) keep working through cuabot's HTTP
API; the `.type` / `.key` methods are now dead code retained for
compatibility but should be removed in a follow-up.

## 2. Clipboard bridge

### The problem

macOS's `NSPasteboard.general` and the sandboxed Chromium's clipboard
(an X11 selection inside the cuabot container) are isolated. Cmd+V in a
v1.5 pane sent the chord to Chromium, which then pasted the sandbox's
clipboard — usually empty.

### The fix

`Diakonos/Services/ClipboardBridge.swift`:

```swift
@MainActor enum ClipboardBridge {
    static func paste(toPort port: Int) async -> Bool   // Mac → sandbox
    static func copyFromBrowser(port: Int) async        // sandbox → Mac
}
```

- **Cmd+V**: read `NSPasteboard.general.string(forType: .string)` →
  `CDPInput.dispatchType(port:, text:)`. The Cmd+V chord is NOT
  forwarded to Chromium; if it were, Chromium would clobber what we
  just typed with an empty native paste.
- **Cmd+C**: evaluate `window.getSelection().toString()` in the sandbox
  via `CDPInput.evaluate`, then write to NSPasteboard. The Cmd+C chord
  IS forwarded so the page's native copy handler runs (it may attach
  richer mime types or trigger a copy-completion side effect).
- **Cmd+X**: same as Cmd+C but forwards Cmd+X. Chromium's native
  handler performs the actual deletion.
- **Cmd+A**: just a chord — no clipboard side-effect. Forwarded normally.

### Edge cases NOT handled

- **Rich text / images**: NSPasteboard supports many mime types; the
  bridge does plain UTF-8 text only. Pasting an image from Preview
  into a chat pane silently does nothing. v1.7 candidate.
- **Cmd+V latency on large strings**: dispatchType sends one CDP event
  per character, in one Python subprocess invocation. A 10K-character
  paste takes ~2-3 seconds. Acceptable; faster path (Runtime.evaluate
  + `document.execCommand('insertText', …)`) was rejected because it
  doesn't reliably fire React's onChange.

## 3. 6-pane mode

### Layout

| Mode | Grid | Positions (reading order) | Cmd+N |
|---|---|---|---|
| 4-pane (default) | 2×2 | TL, TR, BL, BR | Cmd+1..4 |
| 6-pane | 2×3 | TL, TM, TR, BL, BM, BR | Cmd+1..6 |

The toolbar's 4/6 segmented control toggles modes. State persists in
UserDefaults under `workspaceLayout.v2`:

```json
{
  "paneCount": 4 | 6,
  "slots": [ /* always 6 PaneSlot entries in sixPaneOrder */ ]
}
```

`WorkspaceLayout` always stores 6 slots; `paneCount` controls which are
rendered. Switching 6→4 hides `.topMid` and `.bottomMid` but preserves
their state — switching back to 6 restores them.

### v1 schema migration

If `workspaceLayout.v2` is absent, `WorkspaceLayout.init()` looks for
`workspaceLayout.slots.v1` (v1.5's key, length-4 array in
`fourPaneOrder`), promotes those four slots into the 6-slot array, and
fills `.topMid`/`.bottomMid` with `.empty`. The v2 key is written on
the first persist, so subsequent launches use v2 directly.

### 6 → 4 confirm

When the user clicks the "4" segment and `.topMid` / `.bottomMid` have
non-empty kinds, the toolbar shows an `NSAlert`:

> Switch to 4-pane layout?
> These middle-column panes will be hidden but their state will be
> preserved when you switch back to 6-pane:
>   • Claude Chat (was in topMid)

Cancel keeps the current mode. Confirm sets paneCount to 4; the middle
slots remain in storage for restore.

### Sizing

- 4-pane: one column divider (default 50%), one row divider (default 50%).
  Min slot width 220.
- 6-pane: two column dividers (default 1/3 and 2/3), one row divider.
  Min slot width 180. Dividers clamp so each column is at least 10% wide.

On a 1440-wide window in 6-pane, each column is ≈ 480px. On a 1920+
display, comfortable. On a 13" MacBook (1440), borderline narrow for
chat content — acceptable as a power-user feature.

## 4. Half-landed-audit fix

### The pattern

Three places coupled by hand:
- `PaneSlotKind` enum cases (model)
- `EmptyPaneBody.kinds` (dropdown)
- `WorkspaceLayout.title(for:)` (titles)
- `WorkspaceView.accentFor(slot:)` (colors)

Each new pane kind requires touching all of them. v1.3 missed Codex in
EmptyPaneBody; v1.5 missed Claude Chat / ChatGPT in EmptyPaneBody.

### The fix

`PaneSlotKind` gains a `userSelectable` static property:

```swift
static var userSelectable: [PaneSlotKind] {
    let order: [PaneSlotKind] = [.terminal, .claudeCode, .codex, .browser, .claudeChat, .chatgptChat]
    let known = Set(order)
    let missing = allCases.filter { $0 != .empty && !known.contains($0) }
    #if DEBUG
    assert(missing.isEmpty,
           "PaneSlotKind case(s) missing from userSelectable order: \(missing)")
    #endif
    return order + missing
}
```

EmptyPaneBody now reads `PaneSlotKind.userSelectable`. Two guarantees:

1. **Runtime fallback (release builds)**: if a new case is added to
   `PaneSlotKind` but not to the `order` array, it still appears in
   the dropdown (at the end). The bug "shipped without appearing"
   becomes "appeared in the wrong place" — degraded UX, not silently
   missing.
2. **Debug assertion**: in DEBUG builds, the same omission fires an
   assertion at first call site, so the next test/QA run surfaces it
   immediately.

This isn't a true compile-time enforcement (Swift doesn't have a clean
way to express "every enum case must appear in this collection"), but
it's enough to make the v1.3/v1.5 class of bug *impossible* to ship.

## What v1.6 does NOT change

- **Routing verification (claude.ai / chatgpt.com round-trip)** — still
  blocked on Nick logging in. v1.5's checkpoint flagged the same.
- **Image/rich clipboard** — text only.
- **Drag-resize speed** — 6-pane grid uses the same SwiftUI re-render
  on every divider drag. Visible jitter on 13" laptops with chat panes
  is acceptable; not addressed.
