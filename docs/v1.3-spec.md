# Diakonos v1.3 — Polish + Codex + Computer-Use MCP

**Date:** 2026-05-13
**Branch:** `phase/3-v1.3` (cut from `phase/2-v1.2`)
**Status:** Implemented (not merged to main)

## Theme

v1.3 lands four substantive pieces — a Codex pane, a computer-use MCP bridge
so agents can drive the sandboxed Browser pane, dynamic Chromium resize when
the pane changes size, and suppression of the Mac-side Xpra window cuabot
spawns. Plus three v1.2 polish items: an actually-stateful accent picker
(`.tint()` at the App root + persistence), full removal of the API-key
plumbing (Keychain/KeychainStore/EnvironmentBuilder/Agent prefs tab) since
agents auth via their own CLI subscriptions, and a fix to two v1.1/v1.2
silently-broken `xdotool` paths the cua image never supported.

## Codex pane

- `.codex` added to `PaneSlotKind`; appears in the EmptyPaneBody dropdown
  alongside Terminal / Claude Code / Browser.
- `Diakonos/UI/Workspace/Panes/CodexPaneView.swift` mirrors
  `ClaudeCodePaneView`. Spawns `codex --dangerously-bypass-approvals-and-sandbox`
  via `$SHELL -l -c "cd <folder> && exec codex …"`.
- Folder picker chip persisted under `Preferences.codexFolderPath`
  (UserDefaults). Default cwd `$HOME`.
- OAuth handled by `codex login` (Codex's CLI manages it).
- **No auto-trust keystroke injection** — Codex's YOLO flag implies no numeric
  trust prompt. If a future Codex version adds one, mirror the Claude pattern.
- Multiple Codex panes auto-number titles ("Codex", "Codex 2", …).

## Computer-use MCP bridge

### Architecture

- **`Diakonos.app/Contents/Resources/mcp_browser.py`** — a ~190-line
  Python stdio MCP server. No external Python dependencies (mcp SDK
  intentionally avoided to skip pip-install on first run). Implements:
  - JSON-RPC 2.0 over newline-delimited JSON on stdin/stdout.
  - Methods: `initialize`, `notifications/initialized`, `tools/list`,
    `tools/call`.
  - Tools: `browser_screenshot`, `browser_click`, `browser_type`,
    `browser_key`, `browser_scroll`, `browser_navigate`,
    `browser_current_url`.
  - Each tool wraps the cuabot HTTP API at `http://localhost:7842` (the
    same surface BrowserPaneView uses).
- **`Diakonos/Services/MCPRegistration.swift`** — at agent-pane spawn,
  silently runs `claude mcp add --scope user diakonos-browser -- python3
  <path>` (for Claude Code) or `codex mcp add diakonos-browser -- python3
  <path>` (for Codex). Idempotent: removes the existing entry then adds
  fresh, so reinstalls / path changes are honored.

### How it composes with the Browser pane

The MCP tools operate on **the same cuabot sandbox the Browser pane shows**.
Concretely:
- Agent calls `browser_navigate(url=...)` → MCP server hits cuabot
  `POST /bash` to run the Diakonos-installed Python helper inside the
  container → helper issues `Page.navigate` over CDP WebSocket →
  Chromium navigates → screenshot stream in BrowserPaneView picks up
  the new content within ~100 ms.

The agent sees what the user sees, and vice versa.

### Verified end-to-end

```
$ printf 'init\ntools/list\ntools/call{name:browser_navigate, url:https://example.com}'
       | python3 mcp_browser.py
…
{"jsonrpc": "2.0", "id": 2, "result": {"content": [{"type": "text",
  "text": "{\"ok\": true, \"url\": \"https://example.com\"}"}]}}

$ docker exec cuabot-xpra curl -s localhost:9222/json | jq '.[0].url'
"https://example.com/"            # was google.com before
```

## Dynamic Chromium resize

- `BrowserSandbox.setWindowSize(width:height:)` extends the existing
  Python CDP helper (`/tmp/diakonos-nav.py`) with a `resize` action that
  calls CDP's `Browser.setWindowBounds` against the page's window ID
  (obtained via `Browser.getWindowForTarget`).
- `BrowserPaneView` wraps its `VStack` in a `GeometryReader` and runs a
  `task(id: bucketed-size)` that debounces 200 ms before calling
  `setWindowSize`. Size is bucketed to a 16-px grid so divider drags
  don't slam Chromium with per-pixel resize calls.
- The screenshot stream's existing `scale` publish handles the
  coord-translation update automatically.

## Floating Xpra Mac window suppression

- **What we found:** cuabot's container runs `xpra seamless :100`. The
  Mac-side Xpra.app auto-connects to that session and pops a native
  Mac window for each in-sandbox app. Diakonos already shows Chromium
  via its own screenshot stream, so this Mac Xpra window is a
  duplicate the user doesn't want.
- **Suppression:** `Diakonos/Services/XpraSuppressor.swift`. At app
  launch, `pkill -x Xpra` quietly kills it. Because Xpra.app spawns
  *after* Docker/cuabot connects (not at Diakonos start), the killer
  runs as a **monitor loop** every 3 s for the first 60 s of app life.
- **3-dot "Open in floating window"** is the opt-in: it stops the
  monitor, calls `open -a Xpra` to relaunch the Mac window, then
  resumes monitoring after a 30 s grace window.
- **Caveat documented:** this also kills any pre-existing Xpra session
  the user had open for non-Diakonos reasons. v1.4 could check PID
  provenance before killing.

## Accent picker (v1.2 carryover)

- `Preferences.accentColorHex` (`@AppStorage`) persists user choice.
  Default `#2F6BFF` matches v1.2.
- `Preferences.accentColor` resolves it to `SwiftUI.Color`.
- `AccentChipRow(preferences:)` in `PreferenceComponents.swift` is now
  stateful: tapping a chip writes the hex; selected chip gets a
  black-outline ring; row uses `.buttonStyle(.plain)`.
- `DiakonosApp.body` applies `.tint(preferences.accentColor)` at the
  WindowGroup and Settings scenes. This propagates to most controls
  (pickers, sliders, segmented selection, link text, focus rings).
- `PreferencesWindow.sidebar` uses `preferences.accentColor` for the
  selected tab icon.
- `WorkspaceView.accentFor(slot: .browser)` uses
  `preferences.accentColor` so the Browser pane header dot tracks the
  user's choice.
- **Documented gap:** a few legacy callers
  (`DesignTokens.Palette.accentPrimary` in static contexts like
  `WorkspaceDropdown` — already deleted — and a couple of fixed-hex
  uses inside non-pane components) still resolve to the v1.2 default.
  These are visually adjacent; full token-resolver wiring across
  every site is v1.4 work.

## Other discoveries / fixes

### v1.1 / v1.2 silently-broken xdotool paths — fixed

cua's container image does **NOT** include `xdotool`. v1.1 + v1.2 used it
for:
- Browser Reload (F5), Back (alt+Left), Forward (alt+Right)
- Browser pane "navigate" xdotool fallback after CDP helper failed

All of these silently no-op'd via `|| true`. v1.3 replaces them with
CDP equivalents via the existing helper:
- Reload → `Page.reload`
- Back → `Page.navigateToHistoryEntry` (previous entry)
- Forward → `Page.navigateToHistoryEntry` (next entry)

The xdotool fallback in `navigate()` is gone.

The MCP `browser_key` tool still attempts xdotool for special keys
(because we don't have a generic non-Chromium-specific key route),
documented as a known limit — works when xdotool is installed,
no-ops otherwise.
